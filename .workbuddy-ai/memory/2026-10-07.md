## 2026-10-07：watcher 测试失败 ≠ 沙箱限制（真 bug：事件路径与 watch root 拼法不一致）

Rg 贴了一条 `async_watch_loop_indexes_then_flushes_on_shutdown` 的 CI 失败。之前一直按
「沙箱不投递文件系统事件」记在案（5 个测试），**这个归因是错的**。

**根因（macOS，已用探针证实）**：`notify` 的 FSEvents 后端上报的是**规范化后**的路径
（`/private/var/…`），而 `VaultWatcher` 的 root 是调用方给的原样路径（`/var/…`，即
`tempfile`/`TMPDIR` 的拼法）。`map_notify_event` 用 `path.strip_prefix(root)` 映射，失败就
丢事件 —— 实测「5 个原始事件 → 0 个映射成功」，于是 watcher **静默地什么都不索引**。
`/var` 在 macOS 上是指向 `/private/var` 的符号链接，所以这不是边角情况，而是 TMPDIR 下的
默认情况；相对路径 root、以及符号链接的 vault（`~/notes` → `/Volumes/notes`）同样中招。

**修法**：`VaultWatcher::new` 里把 root 规范化一次（`resolve_watch_root`，解析失败就原样保留，
让 `watch` 去报真正的错）。同一个路径交给 `handle.watch`，所以 Linux 的 inotify（回显注册时的
路径、不做规范化）也一致。修完 `async_transport` 3 个失败 + `watch_golden` 1 + `obsidian_compatibility` 1
**全绿**，整个文件从 10.34s 降到 2.07s（10s 死等消失了）。

**另外两个「sleep 赌机器速度」的竞态**（同一个测试里，都改掉了）：
1. 写文件前 `sleep(300ms)` 等 watch 装上 —— 装上之前写进去的文件**一个事件都不会产生**，所以
   这不是「慢一点」而是「永远看不见」。CI 上就是死在这（第 225 行）。改成 `with_ready_signal`
   （`watch_vault` 在 `handle.watch()` 成功后发一次 oneshot），测试等信号而不是猜时间。
   验证方式：临时在安装前插 1.5s sleep，测试照样过（旧的 300ms 预算必挂）。
2. 第二次写之后 `sleep(10ms)` 再发 stop，要求「事件已投递」但「还没到 50ms 去抖窗口」——
   一个 40ms 宽的目标，本地约 1/6 概率失败（`batches >= 2` 拿到 1）。改成窗口 1000ms / 等待
   300ms，两侧都留出余量；20 次连跑 0 失败（改前同一循环出过 2 次）。

**顺手清掉**：`tests/tmp_signal_probe.rs`（自述 "TEMPORARY probe (delete before finishing)"）。
它是 `examples/signal_probe.rs` 的重复件，而且会在 `cargo test --all-targets` 里跑、往**测试进程
自己**发 SIGINT。`examples/signal_probe.rs` 同样带那句注释，但是惰性的（0 个测试），留着没删。

## 2026-10-07（续）：watch 的启动窗口 + 把剩下的 sleep 赌注全部拿掉

Rg 说「继续」，于是把上轮留在「需要拍板」里的两件做完。

**1. 产品 bug：`watch` 在装监听之前先对账**。对账期间发生的编辑不产生事件，事件流也补不回它
没看到的东西 → 「从对账开始到 `watch()` 返回」这个窗口里的写入要等下次启动才进索引。
原来 CLI 的顺序是 `watching the vault` → `service.reconcile()` → `VaultWatcher::new` →
`watch_vault`（里面才 `handle.watch()`）。

修法：把对账搬进 `watch_vault` / `watch_once`，**装完监听再对账**（`watch_once` 顺带改成返回
`(ReconcileReport, WatchReport)`，CLI 的 `--once` JSON 形状不变）。CLI 不再自己对账，两个入口
共用新的 `indexing::watcher::log_reconcile_report` 输出那一行。

顺序为什么是契约而不是实现细节：装好再对账则写入要么被这轮对账读到、要么作为事件投递，
不会两头都漏。这一条同时解释了为什么之前**四个调用点**各自绕着这个顺序打补丁（CLI 自己先对账、
`watch_golden` 和 `async_transport` 各 sleep 300ms、`obsidian_compatibility` 手工先 reconcile）
—— 缺的是 API 里的不变量，不是调用方不小心。

**2. 把三个测试里的 sleep 换成真信号**：
- `async_transport` / `watch_golden` 的进程内 watcher 测试：等 `with_ready_signal`，
  不再 `sleep(300ms)` 猜装监听要多久。语义升级为「已监听且已对完账」。
- 两个 CLI 测试：不再 `sleep(800ms)`，改成轮询「预先存在的 seed.md 是否已进索引」——
  因为对账现在只在装完监听之后跑，这个观察成立即证明监听已装好（新增 `wait_until_indexed` 辅助函数）。
- 投递等待（事件到没到）留成有界余量：sigint 测试 200ms → 300ms，窗口 3000ms 不动。
- `obsidian_compatibility` 删掉自己那次 `service.reconcile()`（库现在按正确顺序做了）。

**3. 文档**：`docs/architecture-guide.md` §3.2 的 mermaid 原来画的是「启动时先全量 reconcile → notify
监听」，正是被改掉的顺序 → 改成「notify 监听 → 装好之后才全量 reconcile」，并补一段说明为什么顺序
是契约、`with_ready_signal` 代表什么。其余 spec / doc 没有钉这个顺序（查过）。

**验证**（都实测过，不是推断）：

  （`watching the vault` → `initial reconcile finished` → `watch batch applied` → `Ctrl-C received`
  → `watch stopped`），stdout 仍是 `{"batches":1}`；`--once` 仍是 `{"reconciled":{…},"applied":{…}}`。
  启动瞬间写入的 `racing.md` 被对账计入（`added=401`）。
- `./scripts/check-rust.sh` 全过；`async_transport` + `watch_golden` + `obsidian_compatibility`

**新增测试与一个诚实的边界**：`ready_means_the_vault_is_already_indexed`（`watch_golden`）钉住
「信号 = 已对完账」这个契约（测试不再重试）。但它**钉不住**「装监听在对账之前」—— 把顺序倒回去

这一点写明了，免得后人以为它覆盖了。
